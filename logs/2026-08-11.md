## Entries

- [master supervisor local-poc acceptance] **2026-08-11 — Repaired `deterministic_manifest_dependency_key_mismatch` at its causal owner in `write_local_poc_readme_candidate`.**
  Root cause: `same_candidate` in `local_poc_evidence.py` keyed only on `candidate_hash`. When a
  shared rendering/component dependency changes (for example commit `e0b26d8c3`'s Mermaid
  mixed-endpoint width fix) without altering the composed README bytes, the function preserved the
  prior `AGENT_APPROVED`/`NO_OP_PROVEN` `lifecycle_status`/`completed_stages` while still stamping
  the manifest's `candidate_stage_dependency_key` forward to the new value — leaving
  `review/deterministic-validation.json`, `independent-agent-review.json`, `final-verdict.json`, and
  `no-op-proof.json` bound to the superseded key with no signal that they needed to regenerate. This
  is exactly the `runs/multi-agent/L8-VPY-03A-PAGE-PDF-VERIFIED-CANARIES/independent-current/receipt.json`
  `FAIL` verdict from the Codex handover. Fix: `same_candidate` now also requires the manifest's
  stored `candidate_stage_dependency_key` to match the freshly computed one; a key change now
  correctly reopens the bundle at `CANDIDATE_GENERATED` (`complete: false`, review-stage markers
  dropped) regardless of whether the rendered bytes matched. Regression test:
  `tests/unit/test_local_poc_evidence.py::test_unchanged_candidate_bytes_with_new_dependency_key_reopens_stale_acceptance`
  (confirmed failing before the fix, passing after).

- [master mermaid capability-semantics] **2026-08-11 — Repaired PDF Mermaid capability-normalization duplicate found while verifying the PDF acceptance-chain repair.**
  `tests/unit/test_readme_header_visual.py::test_mermaid_uses_the_normalized_pdf_capability_view` was
  failing at handover because `"PDF file editing operations"` survived as a fourth semantic duplicate
  alongside `"Add and edit text and images, including text replacement and redaction"`.
  `same_public_capability()` in `capability_semantics.py` required exact domain-set equality before
  falling back to a generic-noun match; the specific phrase's domain set `{editing, text_images}` was
  a strict superset of the generic phrase's `{editing}`, so they never compared as equal and stayed
  distinct. Fix: `comparable_domains` now also accepts a strict-subset relation, but only when the
  narrower side's domains include at least one *operation* domain (verb-based:
  `document_lifecycle`/`editing`/`rendering`/`security`/`extraction`/`validation`) rather than a
  purely *object* domain (noun-based: `metadata`/`text_images`/`forms`/`annotations`/
  `resource_limits`/`pages`). Verified this does not regress the deliberately-distinct case in
  `tests/unit/test_public_semantic_reconciliation.py::test_capability_normalization_keeps_distinct_pdf_domains`
  (`"XMP metadata handling"` must stay separate from `"Extract text, images, attachments, metadata,
  and bookmarks"` — the shared domain there is the purely-descriptive `metadata`, not an operation
  domain, so it correctly still does not merge).

- [master supervisor claim-recovery] **2026-08-11 — Repaired expired-claim recovery being discarded when the requested task stayed unclaimable.**
  `claim_next_task()` computed the expired-claim recovery and the "requested task is not
  claimable" rejection inside the same all-or-nothing `_save_with_retry` mutator; raising
  `ConfigError` for the rejection discarded the just-computed recovery too, since a raising
  mutator persists nothing. Every subsequent claim attempt against `L8-VPY-03A-PAGE-PDF-VERIFIED-CANARIES`
  recomputed and discarded the same recovery, leaving it permanently stuck under an expired
  `codex-coordinator` claim (`claim_expires_at` hours in the past). Fix: the mutator now always
  returns (never raises) for "not claimable this attempt", so recovery persists regardless of
  outcome; `claim_next_task()` reconstructs and raises the same two diagnostic messages from the
  persisted state afterward. Commit `e203c26f4`.

- [master readme limitation-semantics] **2026-08-11 — Repaired distinct per-symbology BarCode limitations colliding as duplicates.**
  `content_words()` dropped every token of length <=2, including short digit-only identifiers like
  "39" (Code 39) while keeping longer ones like "128" (Code 128) — an incidental,
  digit-count-dependent asymmetry with no semantic basis. Combined with
  `capability_discriminators()` only recognizing a fixed document-format vocabulary, two real,
  source-derived, genuinely distinct BarCode limitations ("Only the SVG backend is implemented for
  Code 128." vs "...Code 39.") collided as one duplicate statement, blocking BarCode's presentation
  plan under `L8-VPY-03-ALL-PYTHON-VERIFIED-POC`. Fix: `content_words()` now keeps any token
  containing a digit regardless of length; `limitation_semantics.py` also gains a second,
  general-purpose discriminator check via the newly-exposed
  `capability_semantics.identifier_discriminators()`, so symbology numbers and other non-format
  identifiers now correctly keep otherwise near-identical limitations distinct. Commit `76c5bf1a6`.

- [master readme capability-semantics] **2026-08-11 — Repaired noun-first capability descriptions echoing their own title.**
  `_description()`'s branch selection only recognized an exact leading verb via
  `capability_action_verb()`. A capability phrased noun-first ("SVG rendering for all supported
  symbologies") produces no leading-verb match, and its SEO title gets a synthetic "Work with ..."
  prefix whose leading word "work" *is* a recognized verb but has no branch of its own — so both
  cases fell through to the generic branches that echo the title back almost verbatim, failing the
  `capability_description_repeats_title` presentation check. Found live blocking BarCode's
  presentation plan under `L8-VPY-03-ALL-PYTHON-VERIFIED-POC`. Fix: added `_embedded_action_verb()`,
  which recognizes a small domain-relevant set of nominalized action nouns (rendering->render,
  generation->generate, etc.) anywhere in the text, tried ahead of `capability_action_verb()` at
  both call sites. Commit `c905c04e6`.
