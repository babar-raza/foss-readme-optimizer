- [master readme limitation-semantics] **2026-08-12 — Repaired a same-subject/different-object false-duplicate blocking Font's presentation plan.**
  `public_limitations_equivalent()`'s domain-less fallback path compared only the constraint
  *subject* (text before "requires"/"is"/etc.) once two statements shared no capability domain;
  two statements sharing an identical subject fell through to a fuzzy full-sentence similarity
  check with no regard for what was actually being required. Found live blocking Font's
  presentation plan (`aspose-font-foss/Aspose.Font-FOSS-for-Python`): "Animation path requires at
  least two steps" (`animation.py:693`/`:797`, minimum path waypoint count) and "Animation path
  requires at least 2 frames per segment" (`animation.py:808`, minimum interpolation density) are
  real, independently-triggerable, genuinely distinct exceptions that happen to share the literal
  prefix "Animation path requires" — the shared-subject fast path let them through unblocked, and
  the ~65%-threshold fuzzy match then scored the two "requires at least N ..." sentences as
  equivalent on their shared scaffolding words. Fix: added `_constraint_object()`, extracting
  content words from the text after the predicate with quantifier/determiner scaffolding ("at",
  "least", "exactly", spelled-out and bare numerals) stripped out, so what remains is the noun
  actually being constrained; when both statements share a subject, their objects must now also
  share at least one such word. Verified against the five known-distinct cases already covered by
  `test_limitation_equivalence_rejects_distinct_constraints` and the per-symbology BarCode
  regression test — none reach this branch, so none were affected. New regression test:
  `test_limitation_equivalence_keeps_same_subject_different_object_distinct`. Commit `dde47b0b3`.

- [master presentation claim-matching] **2026-08-12 — Repaired an EOF-boundary false verified-equivalence blocking Words' presentation plan.**
  `equivalent_source_claim_resolution()`'s "identical content, no provenance -> plain preservation"
  escape hatch keyed on strict `content_sha256` equality. When a source claim sits at true
  end-of-file (no trailing newline) and gets literally relocated to a non-terminal position in the
  candidate — e.g. by the "brief-then-collapse" composer feature moving a trailing support/issues
  line into a collapsible details block — the assessor picks up a trailing newline at the new,
  non-EOF position, so the candidate and source spans differ by exactly one boundary byte despite
  being the same text. That spurious hash mismatch defeated the escape hatch, so the claim was
  wrongly classified as `verified_equivalence` (implying a semantic rewrite) instead of ordinary
  literal preservation. The downstream validator (`verified_equivalences_have_exact_candidate_claims`
  in `claim_accountability_validation.py`) then correctly detected, via the composition ledger,
  that this "equivalence" was actually backed by a literal source placement rather than real
  generated content, and rejected it — exactly its documented job. Found live blocking Words'
  presentation plan (`aspose-words-foss/Aspose.Words-FOSS-for-Python`), whose real README ends
  without a trailing newline. Root-caused via a dedicated read-only research agent that reproduced
  the exact failure standalone and pinpointed the failing sub-condition before any fix was written.
  Fix: broadened the escape hatch, still gated behind `not provenance_ids`, to also fire on
  whitespace-stripped text equality — cannot affect any claim carrying real fact-provenance
  bindings, cannot hide a genuine content rewrite since stripping touches only boundary whitespace.
  Verified all four legitimate `verified_equivalence` resolutions in the real repo (two
  comment-stripped-example rewrites, two provenance-backed byte-identical claims) are unaffected,
  and the spurious fifth resolution now correctly falls through to literal preservation with zero
  validation errors. New regression test:
  `test_eof_boundary_relocation_does_not_become_verified_equivalence`. Commit `533db4948`.

  pre-existing local baseline clone) that agree byte-for-byte after line-ending normalization.

  source exists: PyPI returns HTTP 404 for both `aspose-tex` and `aspose-tex-foss`; `git
  ls-remote` shows exactly one ref (`main`, no tags, no releases); git history has exactly two

  tracker has zero issues and zero PRs (open or closed). After completing its own independent
  work, the agent found a pre-existing internal record
