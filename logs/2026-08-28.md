- [requirements] **2026-08-28 — RDM-034: the exact capability-vs-limitation routing mechanism traced**

Continued investigating RDM-034 while the background portfolio pass ran, via static tracing only (read-only, no debug instrumentation this time, no production code changed). Followed the claim-to-fact matching pipeline from `claim_accountability.py`'s `source_records` construction down through `presentation/verified_source_claim_matching.py::equivalent_source_claim_resolution()`: it tries `fact_bound_capability_candidate_claims()` first (requires a candidate claim placed under a `template.section.key_capabilities.claim:` provenance binding in the same byte range as the source claim, plus structured-coordinate or semantic-similarity matching), and only on failure falls through to `fact_bound_limitation_candidate_claims()`. Whichever succeeds sets `capability_reformatted`/`limitation_reformatted`, selecting between `_capability_equivalence_fact_ids()` (keeps every non-identity accepted fact) and `_limitation_equivalence_fact_ids()`. The capability path plausibly fails for this claim because the candidate composed "heuristic PDF/A and PDF/UA checks" into Scope-and-Limitations rather than Key Capabilities — a legitimate compositional choice given the hedging language, not necessarily a bug on its own. The actual defect is downstream, in `_limitation_equivalence_fact_ids()` (`verified_source_claim_matching.py:72-89`): it unconditionally falls back to `facts.selected_fact_ids.get('product.limitations')` whenever no fact in scope has field `product.limitations`, binding to the repository's selected limitations fact regardless of whether that fact's own text is what the claim actually supports. Its own docstring confirms the fallback was added deliberately to fix a different, earlier regression (an over-strict match previously rejecting valid limitation resolutions) — removing it outright would likely reintroduce that bug, so a correct fix needs to distinguish "no literal match because the claim genuinely is the limitation, paraphrased" from "no literal match because the claim is actually a different fact entirely" (this case), consistent with RDM-029's own caution that this area needs narrow, evidence-checked changes, not blanket ones. `fact_bound_limitation_candidate_claims()` itself (which function finds the "exactly one" matching candidate claim triggering this path) was not traced this pass. - [requirements] **2026-08-28 — RDM-034: closed the loop on the proximate cause**

Continued tracing RDM-034 (still waiting on the background portfolio pass) one level further: `fact_bound_limitation_candidate_claims()`'s own match condition (`presentation/verified_source_limitation_matching.py`) requires a scope-and-limitations provenance binding to the limitations fact at the candidate claim's exact byte range, plus `public_limitations_equivalent(source_text, candidate_text)` returning True. Read that function in full (`readme/limitation_semantics.py:87-140`). Found the exact proximate cause: its hedge-word symmetry check (`_LIMITING_LANGUAGE.search()`) only rejects a pairing when exactly one side contains limiting-language vocabulary, and `_LIMITING_LANGUAGE`'s own word list includes `heuristic` alongside `not`/`no`/`only`/`unsupported`. RDM-034's source claim uses "heuristic" as a legitimate capability hedge; the candidate's limitations paraphrase uses the same word as a genuine caveat — both contain it, so the symmetry check doesn't reject the pair. With domain/discriminator/identifier checks also not disqualifying it (both texts share PDF-family format tokens), the function reaches its final fallthrough: `semantically_repeats(threshold=0.5)` (the more permissive of its two thresholds, used when a shared format domain was found) — plausibly clears that bar given the two statements share "PDF/A", "PDF/UA", "heuristic", and "checks" verbatim, despite opposite polarity (one asserts a capability, the other a caveat about it). This is a generic lexical/semantic-similarity heuristic with no explicit capability-vs-caveat polarity discrimination — "heuristic" is simply the word that happens to make this specific pair collide; the same class of false positive could recur for any capability claim whose hedge vocabulary overlaps a limitation's own wording. Not fixed: `_LIMITING_LANGUAGE`, `capability_domains()`, and `semantically_repeats()` are shared low-level primitives used across multiple claim-matching paths, so a change needs portfolio-wide regression testing, not a single-repo check — consistent with the blast-radius caution already recorded. Concrete next step identified: add capability-vs-caveat polarity as an explicit signal to `public_limitations_equivalent()` (e.g. requiring a genuine negation/failure marker on both sides) rather than special-casing "heuristic" out of `_LIMITING_LANGUAGE`, which would likely just move the false-positive surface to the next dual-role word. Logged via `scripts/retrofits/close_rdm034_proximate_cause.py`; `scripts/governance/validate_pinned_hashes.py` (GOV-032) re-ran clean (517 requirement records checked) after regenerating `requirement-taskcard-coverage.json`.
