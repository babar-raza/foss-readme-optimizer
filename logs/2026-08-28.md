- [requirements] **2026-08-28 — RDM-034: the exact capability-vs-limitation routing mechanism traced**

Continued investigating RDM-034 while the background portfolio pass ran, via static tracing only (read-only, no debug instrumentation this time, no production code changed). Followed the claim-to-fact matching pipeline from `claim_accountability.py`'s `source_records` construction down through `presentation/verified_source_claim_matching.py::equivalent_source_claim_resolution()`: it tries `fact_bound_capability_candidate_claims()` first (requires a candidate claim placed under a `template.section.key_capabilities.claim:` provenance binding in the same byte range as the source claim, plus structured-coordinate or semantic-similarity matching), and only on failure falls through to `fact_bound_limitation_candidate_claims()`. Whichever succeeds sets `capability_reformatted`/`limitation_reformatted`, selecting between `_capability_equivalence_fact_ids()` (keeps every non-identity accepted fact) and `_limitation_equivalence_fact_ids()`. The capability path plausibly fails for this claim because the candidate composed "heuristic PDF/A and PDF/UA checks" into Scope-and-Limitations rather than Key Capabilities — a legitimate compositional choice given the hedging language, not necessarily a bug on its own. The actual defect is downstream, in `_limitation_equivalence_fact_ids()` (`verified_source_claim_matching.py:72-89`): it unconditionally falls back to `facts.selected_fact_ids.get('product.limitations')` whenever no fact in scope has field `product.limitations`, binding to the repository's selected limitations fact regardless of whether that fact's own text is what the claim actually supports. Its own docstring confirms the fallback was added deliberately to fix a different, earlier regression (an over-strict match previously rejecting valid limitation resolutions) — removing it outright would likely reintroduce that bug, so a correct fix needs to distinguish "no literal match because the claim genuinely is the limitation, paraphrased" from "no literal match because the claim is actually a different fact entirely" (this case), consistent with RDM-029's own caution that this area needs narrow, evidence-checked changes, not blanket ones. `fact_bound_limitation_candidate_claims()` itself (which function finds the "exactly one" matching candidate claim triggering this path) was not traced this pass. Logged via `scripts/retrofits/sharpen_rdm034_binding_mechanism.py`, appending to RDM-034's existing `acceptance_evidence` (record count unchanged, no `requirements.md` summary refresh needed). `scripts/governance/validate_pinned_hashes.py` (GOV-032) caught the resulting Level-8 graph content-hash drift immediately; regenerated `requirement-taskcard-coverage.json` and re-ran the validator clean (517 requirement records checked).
