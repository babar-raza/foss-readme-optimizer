# Project Log — index

Dated historical record for `plans/master.md`, `plans/requirements.md`, and `plans/GOVERNANCE.md`.
None of those three narrates history (`GOVERNANCE.md` rule 1/6) — every "what changed and why"
question is answered here instead. Investigation findings/evidence still live in
`plans/investigations/` (unchanged) — this log is for dated narrative about the plan trio, not a
second home for research write-ups.

**What belongs here:** master-plan decisions and status changes, requirement additions/status
moves, GOVERNANCE.md rule changes, wave/phase completions, bugs found and fixed, backlog findings
logged, safety/credential incidents — anything this project would previously have written as a
Changelog line in `master.md` or `requirements.md`.

**Format**, one entry per change, first line only:
`- [tag] **YYYY-MM-DD** — <what changed> — <one-clause why>`
Multi-paragraph entries are fine for genuinely substantial changes (this log's own migrated
history is the precedent) — one-line is the default, not a hard cap.

**Tags** (first-line prefix, space-separated, source tag required, `incident` optional):
- `master` / `requirements` / `governance` — which document the change belongs to.
- `incident` — combine with a source tag for safety/credential/security incidents, so they stay
  independently greppable (`grep incident logs/*.md`) instead of buried in prose.
- `auto-skeleton` — this entry was mechanically generated by `heal_log_coverage.py`, not
  hand-authored. It records the covering commit(s) accurately but has no root-cause/fix narrative
  yet. Find every one needing a human/agent enrichment pass with `grep auto-skeleton logs/*.md`;
  enrich by editing the shard directly (an auto-skeleton is the one entry shape it's fine to
  hand-edit in place, since it isn't hand-authored to begin with) and dropping the tag once it
  reads like a normal entry.

**Maintenance — two touches per new entry, same discipline as Decision Ledger + Changelog always
was:**
1. Append the entry to today's shard (`logs/<YYYY-MM-DD>.md`; create it, copying the shard header
   below, if this is the day's first entry) via `scripts/governance/append_log_entry.py` — never
   hand-edit a shard directly (the one exception is enriching an existing `auto-skeleton` entry,
   above), since two independent writers of the same format drift out of sync.
2. Add one row to that shard's own local index table — `append_log_entry.py` does this for you;
   pull the decision numbers / requirement IDs / wave-or-phase numbers straight out of the entry
   you're writing, you already know them, this isn't a research step.
3. ~800 lines is the *typical-day* target this guidance is calibrated for, not a hard cap — an
   exceptionally dense single day (this project's own 2026-07-19, at 974 lines, is the precedent)
   is real content, not a sharding failure, and isn't force-split. Only split a single day further
   (`<YYYY-MM-DD>-a.md`/`-b.md`, chronological within the day) once it clears roughly double that
   (~1,500 lines) — same "split before you extend" smell test `GOVERNANCE.md` already applies to
   code (~300 lines/module), calibrated up for how dense one real day of this project can get.

**This is enforced, not just documented** — 10 real days went missing before it was (see the
`auto-skeleton`-tagged entries and the decision recording this redesign for the full account).
Three independent layers, each closing a gap the one before it can't:
1. `validate_plan_structure.py`'s `check_governed_edits_paired_with_log_entry`, wired into the
   local pre-commit hook and every CI run, blocks a commit/push that edits `plans/master.md`,
   `plans/GOVERNANCE.md`, `plans/requirements.md`, or either decision/requirement `catalog.jsonl`
   with no paired `logs/` change in the same change. Only protects a clone with hooks installed —
   a hookless clone, a `--no-verify` commit, or a direct API commit bypasses it by construction.
2. `.github/workflows/log-coverage-heal.yml` runs on every push to `main` regardless of which
   agent or environment made it, and self-heals: any governed edit still missing a `logs/` entry
   gets an auto-generated, `auto-skeleton`-tagged entry committed straight back to `main` within
   the same CI run — this is the actual guarantee, since it depends on no agent's compliance.
3. `.github/workflows/log-coverage-audit.yml` sweeps full history daily as a path-independent
   backstop, and deliberately fails loud (not silently green) if it ever finds anything — that
   means layers 1-2 both missed something in real time and it needs investigating, not just
   patching over quietly. Bounds worst-case drift to one day even if every other layer fails at
   once.
