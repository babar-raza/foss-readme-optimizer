- [fix] **2026-08-29 — VER-012: the reviewer double was answering for a reviewer that never ran**

The two long-tracked failures were never a compact-grounding-retry gap. Both tests patched
`separated_readme_review.build_live_merged_review_client`, but `run_merged_readme_review` routes to
the bounded/separated reviewer for every candidate carrying a document plan (`6591c6cc2`, "route by
rubric evidence, not candidate size") — which is every candidate the `project` fixture builds. So
the override landed on a reviewer that never executed, the fixture's own always-accepting
`_fake_accepting_role_clients` stayed in charge, the candidate was accepted on the first round, and
the repair loop the tests exist to exercise was never entered at all
(`statuses.count("AGENT_REVIEWING") == 1`, not 2).

A previous cycle tried rewiring to `build_live_role_review_clients` alone and correctly reverted it
rather than leaving a half-migration: that alone moves the failure to
`independent_review_exception:StopIteration`. The reason is that
`_RejectThenAcceptBlindReviewClient` was written for the merged reviewer, which sees the whole
candidate in one call, so "reject on call 1" was the same thing as "reject the overview diagram".
Bounded review sends one packet per section, so call 1 is whichever section happens to be packed
first, and the double's `next(... startswith("```mermaid"))` raised the moment that section held no
diagram.

Migrated the double to the bounded contract: it selects the packet that actually contains the
mermaid anchor rather than a call ordinal, and rejects exactly once. That target is load-bearing,
not cosmetic. `readme_repair_validation.py::build_repair_receipt` only marks a finding
`addressed_pending_rereview` when the finding's own section text changes, an operation bound to it
changes, *and* its quoted span stops occurring — and `_RepairAwareCompositionForcedToolClient` is
the thing that makes all three true, by re-planning that diagram. `rereview_authorized` further
requires *every* finding to be addressed, so a rejection aimed anywhere the repair client does not
rewrite would end the loop instead of exercising it. `product_specificity` stays in scope under
`bounded_review_visitor_scope.py` (it is in `_COMMON_CRITERIA`, hence in
`_CRITERIA_BY_ROOT["at-a-glance"]`), so no grounding retry is forced.

Assertions moved to the bounded contract. Finding ids are packet-namespaced
(`pkt.visitor.0002.at.a.glance.9c47a37ecc7c.quality.generic-overview`), and asserting the namespace
alongside the id is strictly stronger than the old bare equality — it also proves the rejection
landed on the at-a-glance packet. The per-round call literals (`== 1`, `== 2`) were replaced by the
relationships they stood for: exactly one rejection, after-rereview count strictly greater than
before, and the accepted rerun leaving both counters untouched. A fixed number there would encode
today's section packing rather than the contract.

Proved non-vacuous by restoring the pre-fix wiring in place: both tests fail with it, both pass
with the migration. VER-012 stays `PARTIAL` — the `compact_grounding_retry` shape its requirement
text actually names is still avoided (via `markdown_integrity`, the one criterion every
`_CRITERIA_BY_ROOT` entry admits) rather than handled.

**Recorded separately, because it invalidates a number:** the baseline suite run taken at the start
of this cycle reported 8 failures, 6 of them in `test_mission_execution_guard.py`. Those 6 are not
regressions. That file reads the real `level8-autonomous-mission-task-graph.yaml`, and
