  via SHA-256: `180a16f7...`). A full pytest run afterward confirmed exactly the pre-existing
  9-failure baseline, zero regressions. Lesson: never run a real, non-test candidate-generation
  call with `force_regenerate=True` against a path that doubles as a pinned test fixture without
  first checking whether it's gitignored/exempt from `git checkout` recovery.

- [master] **2026-08-17** — **The main finding of the day.** Root-caused why the local README
  portfolio was stuck near 4/33 candidates despite this session's earlier T3/T4 aspose.org-check
  wiring: `api.public_surface` (the fact that gates whether a candidate can render a real API
  Reference section — `presentation/verified_source_detail_routing.py::_api_reference_available`)
  was populated for Python only, via this repo's own separate AST-based extractor
  (`curated_python_public_surface.py`). No other platform had an equivalent, so every non-Python
  product either silently got no API Reference section or crashed
  (`ValueError: valuable source detail has no canonical presentation destination:
  ...:api_public_surface`, observed live on `Aspose.Cells-FOSS-for-.NET`). Investigated
  aspose.org's own real pipeline (`D:\onedrive\...\aspose.org`) to find the actual source of their
  own candidates' API Reference tables: traced two layers deep — `content/reference.aspose.org/`
  (their published docs mirror) is itself LLM-composed *from* `knowledge/{family}/{platform}/
  merged/api_surface.json`, the real ground truth: a per-language, source-level static-analysis
  extractor (`scripts/pipeline/extraction/scout.py`, citing exact `.cs`/`.java`/etc. source files
  and line numbers). Found this exact `api_surface.json` data was **already imported into this
  repo** (`data/imported/knowledge/{family}/{platform}/merged/api_surface.json`, all 31 needed
  family/platform pairs, committed back in `3e3fd55fb6`, T1A/T1B) — just never wired to a fact
  detector. Added `detect_api_public_surface` (`aspose_detectors.py`, T4's 12th adapted piece) to
  read it directly and project it into the `api.public_surface` field via `composer_factpack.py`'s
  `aspose_fact_records`. Live-verified: `Aspose.Cells-FOSS-for-.NET` now generates (`status:
  GENERATED`, was a hard crash before) with a real, correctly-formatted `## API Reference` section
  (collapsible Core API table, 96 real public types, real class descriptions) matching the shape
  of aspose.org's own proven candidates. No new large data import was required — considered and
  rejected syncing the 62-file/72MB `api_surface.json` tree fresh from aspose.org's repo (would
  have permanently bloated this repo's git history by that much) once the already-committed local
  copy was found to already cover every product needed. Full-portfolio regeneration in progress
  at time of writing to measure the real coverage impact.

- [master governance] **2026-08-17** — Added AGENTS.md rule 15 ("Extending the runtime" section):
  the "sole production runtime" discipline (rules 1-14) binds an agent's own verification workflow,
  not only new capability authoring. Direct cause: earlier today's `runs/baseline/` fixture
  corruption incident (see above) happened because a real-repo verification check was done by
  importing and calling `readme_agent.capabilities.render_readme_candidate.execute()` directly in
  a standalone script instead of going through `readme-agent supervise --repo ...
  --bounded-verified-canary --execution-profile local_poc`, the actual governed mechanism for
  exactly this — bypassing state, evidence, authorization, and independent-verification recording
  entirely. Codifies the fix as a standing rule rather than a one-off correction.

  cannot mechanically re-derive — a genuine, safety-relevant design question given this project's
  standing "LLM must not invent facts" constraint, not a bug. Documented as the concrete next
  design decision; no code change attempted.
