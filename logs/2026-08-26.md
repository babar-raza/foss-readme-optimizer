## Entries

- [master] **2026-08-26 — Windows MAX_PATH: bounded-review cache preservation actually runs**

`preserve_bounded_review_cache()` had three independent long-path blind spots on Windows: its own entry guard used unprefixed `Path.is_dir()`, which returned `False` for a genuinely-existing 372-character cache directory and silently skipped preservation entirely; `TemporaryDirectory(dir=...)` and `shutil.copytree()` had no long-path handling of their own. All three now route through `evidence/writer.py::win_long_path()`. New regression coverage (`tests/unit/test_local_poc_review_cache_preservation.py`) exercises the long-path round trip, the short-path case, and the no-cache pass-through.

- [master] **2026-08-26 — `force_rmtree` closes a transient WinError 145, unmasking two stale test fixtures**

Fixing the cache-preservation bug above let `archive_and_prune_downstream_artifacts()`'s downstream-pruning `shutil.rmtree()` actually execute for the first time in a real integration test, immediately hitting a transient Windows `WinError 145` ("directory not empty") — the same back-to-back-read pattern SCL-010 already documented in `gitsafety/clone.py`. Routing that call through the existing `force_rmtree()` helper fixed it. That, in turn, exposed two pre-existing test-fixture gaps from the same day's earlier `fix(review): route by rubric evidence, not candidate size` commit: `test_supervisor_loop.py`'s shared `project` fixture never faked `build_live_role_review_clients` (only the merged-review client), and `review_role_fixture_support.py`'s catalog parser expected dict-shaped rows when production has always emitted compact `[anchor_id, text]` pairs. Both fixed; verified against 146 unaffected tests across three sibling review test files plus the full `test_supervisor_loop.py` suite (79 passed, 4 failed on the newly-isolated VER-012 gap below).

- [requirements] **2026-08-26 — VER-012: offline bounded-review fixture has no compact-retry branch**

`run_grounded_role()` deliberately drops the catalog-bearing prompt on a grounding retry, substituting a compact reconciliation turn — by design, for token economy. The offline test fixture (`GroundedAcceptingRoleReviewClient`) was only ever written against the first-attempt message shape and crashes instead of producing a second corrected response. Affects four tests in `test_supervisor_loop.py`; two independent unknowns remain (why the first attempt fails grounding in this scenario, and how to safely reconstruct a response from only the compact payload) that need their own investigation.

- [requirements] **2026-08-26 — RDM-029: dropped source claims never get an authored resolution**

The fleet's single most-repeated blocker ("claim accountability has N blocking claim(s)") is not a gate bug: 16 of 18 observed blocking IDs are inherited vendor-README claims the compose stage correctly drops as unsupported-format boilerplate, but for a recurring subset never authors the `verified_omission`/`presentation_policy_correction` resolution the accountability gate requires. Confirmed across `aspose-page-foss`, `aspose-pdf-foss` (Python/.NET), `aspose-cells-foss` (.NET/Java/Rust/Go), and `aspose-slides-foss` (Java) — six repositories, three ecosystems, `consecutive_failure_count` as high as 30 with no self-healing. Traced the gap one layer deeper than the original finding: `verified_source_policy.py::build_verified_source_policy_edits()` generates edits for four span kinds (shell-policy boilerplate, Aspose links, enterprise terminology, public-text corrections) but has no fifth generator for unsupported format/role claims — the exact detection `presentation_lint_structure.py`'s `format_direction_contradiction` check already performs, just reactively. All three files in the resolution chain match the `presentation/verified_*.py` document contract glob, so this cannot be fixed mid-fleet-pass without invalidating every repository's cached composition plan.

- [requirements] **2026-08-26 — RDM-030: API reference descriptions collide across unrelated types**

`aspose-pdf-foss/Aspose.PDF-FOSS-for-Java` reproducibly fails "API reference contains duplicated descriptions" at the same revision across two separate fleet runs. Root-caused via live reproduction against the real product facts: `role_sentence()`'s name-derivation fallback lets `PdfFont`'s suffix-stripped prefix and `Font`'s empty-suffix family-name fallback both canonicalize to "PDF", rendering two genuinely distinct, real-Javadoc-backed types to the identical sentence — the renderer never reads the fact's own description text at all. Contract-bound (`presentation/verified_template_api_descriptions.py`/`verified_template_api_text.py`), not fixed mid-pass.

- [master requirements] **2026-08-26 — Two quick_start authoring false positives fixed for aspose-pdf-foss**

`section_authoring_fact_validation.py` blocked `aspose-pdf-foss` twice, once per ecosystem, for reasons its own example code disproved. C++'s construction-claim authorizer only recognized assignment-style construction (`Type var = Type(args)`); C++ direct-initialization (`Aspose::Pdf::Document doc("input.pdf");`) has no `=` at all despite unambiguously constructing an object, so "create"/"instantiate" claims about the example were rejected as unsupported. .NET's format-token extractor treated a filename literal like `"output.pdf"` as one compound token that `canonical_document_format()` rejects whole, so the format the example obviously writes was never authorized. Both fixes are strictly additive (more patterns recognized, none removed); neither touched file is document-contract-bound, so this landed safely mid-fleet-pass. Verified via new regression tests (`test_section_authoring_fact_validation.py`, including a negative control distinguishing direct-init from a plain member call) plus the full section-authoring suite (103 passed).

- [master] **2026-08-26 — First full portfolio acceptance: `aspose-3d-foss/Aspose.3D-FOSS-for-Python` reaches `NO_OP_PROVEN`**

A targeted single-repo retry (`portfolio-proof --mode fleet --only ... --retry-blocked`) advanced this repo from a stale `README_ASSESSED` state (a failed repair from 2026-08-24 that never touched every reviewer-flagged span) all the way to `AGENT_APPROVED`, then a second immediate retry promoted it to `NO_OP_PROVEN` with zero new provider calls, confirmed via the durable lifecycle history. On the way there, a false alarm: querying the repo's durable state with the default `GitStateBackend()` (pointed at `origin`) showed it stuck at `README_ASSESSED` from two days ago, while `local_poc`/`portfolio-proof` actually track state in a *separate* local bare git remote (`runs/local-poc-state/state.git`, via `default_local_poc_state_backend()`). Querying the correct backend showed the real, current, successful progress. Logged as a reference memory to prevent the same 20-minute detour in a future session. Dashboard now shows `accepted_30_of_30=1` for the first time this session.

- [master requirements] **2026-08-26 — RDM-029 fixed: unauthorized source format claims omitted at compose time**

With the fleet pass complete (no longer in flight), it was safe to touch the document-contract-bound resolution chain. Added a fifth edit-generator to `verified_source_policy.py::build_verified_source_policy_edits()`, reusing `presentation_lint_format_directions.py`'s own directional-fragment scanning (exported as `directional_fragments`) and `unsupported_format_directions()` rather than reimplementing either -- deliberately mirroring the exact detection the downstream candidate-side lint already performs, so an input/output claim the accepted `product.formats` fact does not authorize is now omitted deterministically at compose time instead of surfacing later as an unresolved claim-accountability block. Verified via a live reproduction against real `aspose-pdf-foss` product facts (correctly omits an unauthorized "export to PDF" claim, correctly leaves an authorized XLSX claim untouched) plus a 27-file, 490-test regression sweep: 487 passed; the 3 remaining failures were confirmed pre-existing and unrelated via git-stash isolation (logged separately as VER-013).
