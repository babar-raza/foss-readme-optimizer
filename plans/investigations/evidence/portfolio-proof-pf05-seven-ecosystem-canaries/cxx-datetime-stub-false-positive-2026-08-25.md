# C++ `DateTime` "unimplemented stub" claim is a false positive

## Context

After PF05-CXX-LINK-001 was resolved (commit `e2db75462`, `fix(links): exclude
code-span sample data from Aspose link governance`), rerunning the bounded C++
canary (`aspose-cells-foss/Aspose.Cells-FOSS-for-Cpp` @
`9f852d0ff1cfdad2d661556d6b87a8eff8c063a2`) advanced past the link-validation
boundary and surfaced the next one: `presentation_plan` now blocks on four
findings.

```
claim accountability has 2 blocking claim(s): source:claim:32306:9fb423fd68ca9094, source:claim:32674:b6dcdc6c7bf9fbe7
presentation.semantic_duplicate.7f247683b2ff: Capability information is repeated across competing visitor sections.
public_quality.malformed_low_information_prose.6bec24bc9114: Capability information is repeated across competing visitor sections.
public_quality.contradiction_capability_symbol.4fdfcf7f20cc: `DateTime` is described as available in one section and explicitly unsupported or unimplemented in another.
```

This note records the root cause found for the fourth finding
(`contradiction_capability_symbol` on `DateTime`) before handing it off as a
properly-scoped backlog item, rather than rushing a fix into vendored,
integrity-checked code.

## Root cause (confirmed against real upstream source)

`facts/product-facts.json` for this repo carries a `limitation` claim:

```
claim_id: cells/cpp/CLM-cells-06e58f62c1652767
text: "Unimplemented stub (empty body): DateTime in Aspose.Cells.Foss.Cpp/src/DateTime.cpp:77"
confidence: 1.0
```

This claim is **false**. Fetched the real file at the exact snapshotted
revision (`gh api -H "Accept: application/vnd.github.raw"
repos/aspose-cells-foss/Aspose.Cells-FOSS-for-Cpp/contents/Aspose.Cells.Foss.Cpp/src/DateTime.cpp?ref=9f852d0ff1cfdad2d661556d6b87a8eff8c063a2`).
Line 77 is:

```cpp
DateTime::DateTime(int year, int month, int day, int hour, int minute, int second)
    : _ticks(DateToTicks(year, month, day, hour, minute, second))
{
}
```

This constructor is fully implemented -- its real work happens in the
member-initializer list (`: _ticks(DateToTicks(...))`), which is completely
idiomatic, correct C++. The `{}` body being empty is normal, not a stub.

The claim is generated by
`vendored_asposeorg/scripts/pipeline/extraction/scout.py::_detect_cpp_stubs()`,
which walks tree-sitter `function_definition` nodes and flags any whose
`compound_statement` (body) has zero meaningful statements as an
"unimplemented stub." It does not check for a sibling `field_initializer_list`
node (verified empirically: for a constructor with an initializer list,
tree-sitter's cpp grammar places `field_initializer_list` as a **sibling** of
`compound_statement` under `function_definition`, not nested inside it -- see
the reproduction below). Any C++ constructor written in the idiomatic
initializer-list-does-the-work / empty-body-block style will be misclassified
as an unimplemented stub by this heuristic.

Reproduction (`tree_sitter_language_pack.get_parser("cpp")`):

```
function_definition
  function_declarator -> 'DateTime::DateTime(...)'
  field_initializer_list -> ': _ticks(DateToTicks(...))'
    field_initializer -> '_ticks(DateToTicks(...))'
  compound_statement -> '{\n}'
```

vs. a genuine stub (`int Foo::Bar() {}`), which has no `field_initializer_list`
sibling at all.

## Why this was not fixed directly this session

`scout.py` lives under `src/readme_agent/vendored_asposeorg/`, a byte-integrity
checked import from aspose.org's own generator pipeline at a pinned
`source_commit`. `tests/unit/test_aspose_org_vendored_source.py::
test_vendored_source_rejects_changed_bytes` proves
`facts/aspose_org_vendored_source.py::load_vendored_aspose_org_source()`
deliberately rejects any drift between the vendored files' live bytes and the
recorded manifest (`data/imported/aspose_org_knowledge_generator_manifest.json`,
per-file `sha256`/`git_blob`). A direct patch to `scout.py` (attempted, then
reverted this session -- see git history around this evidence file's commit)
breaks that integrity gate.

Separately, `facts/knowledge-generation.json` for this run shows
`"status": "reused"` from a cache keyed by
`(org_repo, source_revision, generator_source_commit, generator_sha256)` at
`runs/knowledge/r/.../g/.../knowledge/cells/cpp/merged/`. Any legitimate
`scout.py` fix changes `generator_sha256`, which would invalidate every
already-cached C++ (and any other native-language constructor pattern this
heuristic affects) knowledge-generation bundle across the whole portfolio --
the same cache-invalidation-blast-radius concern already logged as `CORE-035`.

The correct fix therefore belongs at this repo's own consumption layer (where
imported claims become `ProductFactsV2` facts -- `facts/aspose_knowledge_claims.py`
/ `facts/aspose_knowledge_selection.py`), corroborating or filtering
`kind: "limitation"` claims of this exact shape against real source before
acceptance, mirroring the existing LLM claim-disposition corroboration
pattern (never trust a raw claim; independently re-check it) -- or, upstream,
via a legitimate re-vendor sync that updates both `scout.py`'s bytes and the
manifest together. Either path is a properly-scoped change touching shared
fact-acceptance machinery for every native-language repo in the portfolio, not
a same-session micro-fix. Logged as `CORE-038` (BACKLOG).
