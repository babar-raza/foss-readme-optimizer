# Portfolio README Proof Contract

`execution_authority: false`

This contract defines the bounded portfolio-proof campaign selected by the sole Level-8 mission
graph. It does not create a second plan, queue, controller, or mutable cursor. The graph declares
task order; durable supervisor state alone owns claims and transitions.

## Outcome

At the baseline `RegistryRevisionV1` frozen from `data/products.json` at optimizer commit
`df864ffd189167ef7e3cd458fb092c704769babe`, 33 repositories are admitted: 31 contain substantive
product evidence and are README candidate targets; two PSD repositories contain only a README and
receive an evidence-bound `NON_PROCESSABLE_NO_IMPLEMENTATION` disposition. The delivery numerator is
therefore **31/31 processable repositories**, not 31/33 and not a fabricated 33/33.

The numbers above describe this baseline, not an immutable portfolio constant. Every campaign
freezes a content-addressed registry revision. Discovery or admission growth reopens processability
and the affected portfolio closure; the current processable denominator is always derived from that
revision.

## Candidate Acceptance

A processable repository is complete only when one exact candidate passes all of these boundaries:

1. current immutable repository snapshot and complete processability decision;
2. repository-grounded facts and qualified development-time knowledge;
3. complete candidate composition with source-content dispositions;
4. every applicable blocking check in the independently qualified, bound check-registry revision
   runs and passes, while skipped, errored, unclassified, stale, or unevaluated checks remain
   visible and cannot be counted as passing;
5. independent factual and visitor-quality review of the exact candidate bytes;
6. criterion-specific evidence for all 30 rubric points and zero hard disqualifiers;
7. immediate unchanged complete-transaction replay with identical candidate/evidence identities,
   zero new provider work, and no duplicate lifecycle effect;
8. checksum-complete reconstruction from authorized immutable artifacts.

The state `AGENT_ACCEPTED_30_OF_30` is distinct from human acceptance and publication eligibility.
The campaign terminates at `PORTFOLIO_AGENT_ACCEPTED_AWAITING_GLOBAL_HUMAN_REVIEW`; it does not
authorize a product write or claim the complete `plans/idea.md` mission.

## Processability

Processability is established before authoring/provider work from a pinned repository snapshot and
inventory. A non-processable disposition must record repository identity, source revision,
inventory hash, reason, evidence, zero authoring/provider work, and a resume predicate. README-only
is not a universal exclusion rule: future repositories with authoritative README, metadata,
history, license, or approved public evidence may use an explicit README-only profile. The two PSD
repositories satisfy the narrower baseline disposition because no implementation or other
substantive product evidence exists at the pinned revision.

Missing a repository license file does not block unrelated README work. License prose requires
repository evidence or a versioned approved policy fact, and any contradiction blocks that prose.

## Development-Oracle Refresh And Qualification

Aspose.org is useful because it evolves against the same product portfolio; it is not assumed to be
complete, correct, internally consistent, or suitable for this system without adaptation. A refresh
is a controlled source qualification, not a directory copy and not an automatic promotion of every
new check to a hard gate.

The 2026-08-20 recon binds committed Aspose.org revision
`bf9381af81415843a36a8f50cb6415e01f03ad55`. Its committed
`readme_refresh_checks.py` exposes 103 `check_*` functions: 97 participate in ordinary complete-
candidate evaluation and six are auxiliary surgical-scope or upstream-issue checks. The optimizer's
current 89-function snapshot from `7f72da4e1423546104b40fa8cebf5b9ae3ce9c91` is therefore stale.
Fourteen functions are absent locally; ten affect ordinary candidate qualification and four affect
auxiliary scope/issue workflows.

Before candidate sealing, the owning graph task must:

1. import only committed blobs and record upstream commit, blob hashes, module/check version, source
   inventory, and the local import manifest;
2. diff the current knowledge-generation mechanism and its exported corpus, check module, runner
   inputs, schema validators, link/diagram data, fixtures, and skill contract against the bound
   local snapshot; prove which facts the generator derives from the shared source repositories and
   whether this repository can reproduce them independently;
3. port the ten missing candidate checks plus only their necessary pure dependencies and typed input
   contracts; retain the four auxiliary checks for the workflow stages where they are applicable;
4. regenerate the complete check classification from actual runner usage and declared severity,
   then independently qualify every check against local semantics, real-repository fixtures,
   negative controls, and the approved presentation contract;
5. classify each upstream item as `ADOPTED_EQUIVALENT`, `ADAPTED`, `DIAGNOSTIC`, `QUARANTINED_DEFECT`,
   `NOT_APPLICABLE`, or `DEFERRED_INPUT_GAP`, with a reason and evidence;
6. promote a check to blocking only when its inputs exist, its semantics agree with this contract,
   evaluator errors fail closed, and empirical controls show no unresolved false positive;
7. add a currency tripwire that detects upstream inventory/hash drift without silently changing the
   deployed acceptance contract; and
8. prove the resulting local check battery with Aspose.org unavailable.

The import should reuse current dependency truth, diagram geometry, content/disposition, SEO,
knowledge extraction, and candidate-validation behavior where it survives qualification. The local
system must own the resulting generator, schemas, tests, manifests, and refresh command so future
knowledge can be recreated from the product repositories without Aspose.org. Candidate-store,
surgical-scope, per-block acceptance, anti-stall, and acceptance-registry mechanisms are patterns to
adapt behind this repository's typed contracts, not a replacement controller. Dirty sibling working-
tree bytes, task state, caches, generated candidates, and unqualified prose are never imported as
authority.

## Editorial And Repeatability Contract

LLM work is bounded structured judgment, not one unrestricted whole-README rewrite and not a fixed
number of calls. A changed repository may use separately schema-validated jobs for repository
interpretation, document planning, section prose, isolated review, and finding-scoped repair. Every
factual selection cites accepted evidence IDs. Commands, coordinates, URLs, badges, inherited code,
Markdown structure, Mermaid syntax, source spans, and effects remain deterministic. Author and
reviewer contexts, identities, prompts, and caches remain separate. At most two finding-scoped repair
rounds are permitted before the first failing causal owner becomes a graph task.

Each repository transaction is content-addressed by at least:

- source revision and exact source README hash;
- fact-contract, imported-corpus, selected-bundle, and selector hashes;
- prompt registry, declared model route/revision, and structured-output schema hashes;
- presentation-component, validator/check-registry, and reviewer-standard hashes;
- protected-content and runtime-profile hashes.

The first accepted execution persists exact validated structured decisions and candidate bytes.
An identical execution verifies checksums and reuses those artifacts with zero provider calls.
Source/fact changes reopen facts; knowledge changes reopen selection; prompt/route changes reopen
editorial planning; component changes reopen rendering; check changes reopen deterministic
validation; reviewer-standard changes reopen review; effect credentials change only a later effect
stage. Provider nondeterminism is therefore contained by immutable accepted artifacts rather than
repeatedly re-asking the model.

Aspose.org candidates are a development oracle for obligation and information-coverage comparison,
never wording comparison. A discovered gap is repaired at its native causal owner: extraction,
knowledge selection, structured composition, deterministic rendering, validation, or review. The
comparison does not enter acceptance or deployed inputs.

## Refreshable Visitor-Quality Benchmark

The development benchmark is the latest complete, stably synchronized canonical Aspose.org
`reports/repo-presenter-regen-full` tree available when a campaign is frozen. Generated reports may
be intentionally gitignored, so refresh binds committed producer code separately from generated
output:

1. record Aspose.org Git HEAD and a redacted dirty-tree fingerprint;
2. inventory every candidate, disposition, verification receipt, comparison report, and aggregate
   report under the canonical generated root;
3. repeat the inventory after quiescence and require identical path, byte, and checksum sets;
4. reconcile candidate, per-repository-receipt, and aggregate-audit denominators; and
5. run a fresh aggregate audit against the frozen generated bytes.

The benchmark state machine is `BENCHMARK_DISCOVERED -> BENCHMARK_STABILIZING ->
BENCHMARK_SNAPSHOTTED -> BENCHMARK_AUDITED -> BENCHMARK_QUALIFIED ->
BENCHMARK_PROFILE_FROZEN`. A changing tree enters `SOURCE_MUTATING`; missing receipts or denominator
mismatch enter `INCOMPLETE_SYNC`; audit failures remain item-level `BENCHMARK_ITEM_FAILED`.
Unaffected local work may continue, but none of those states can weaken candidate acceptance or
masquerade as a complete benchmark.

Refresh creates `DevelopmentBenchmarkSnapshotV1`, binding producer HEAD/dirty fingerprint,
twice-stable generated-tree inventories, product inventory, every README/disposition/verification/
report hash, current check inventory, and the fresh sibling portfolio-audit result. The campaign then
derives a locally qualified `BenchmarkQualityProfileV1`; neither the sibling path nor raw candidate
bytes enter deployed inputs.

Qualification distinguishes benchmark quality from benchmark authority:

1. every benchmark repository is inventoried, including candidates omitted from its own aggregate
   audit, missing receipts, current hard-gate failures, published-skip states, and stale reports;
2. only locally verified, applicable patterns become profile obligations; a failing or unproved
   benchmark candidate remains diagnostic and never lowers local acceptance;
3. the profile measures structure and navigation, product-specific opening, branding/visuals,
   capability depth, installation/dependencies, source-derived examples, API-reference coverage,
   documentation/resources, limitations, development/testing, licensing, inherited-content
   dispositions, public tone, and absence of internal process narration;
4. a local candidate must pass every native hard gate and be no worse than the accepted benchmark on
   applicable material information coverage; stylistic wording and document length are not copied or
   mechanically maximized;
5. local repository truth always wins. Benchmark claims are hints to inspect, not accepted facts, and
   every final claim still requires current-source `ProductFactsV2` authority;
6. a benchmark refresh reports `BENCHMARK_REFRESH_AVAILABLE` and reopens only the affected
   calibration/profile stage at a declared campaign or cohort boundary. It never silently changes an
   in-flight campaign or invalidates unaffected accepted bytes; and
7. the sibling checkout can be removed after snapshot qualification; candidate generation,
   validation, review, no-op, and deployed operation must still succeed.

The 2026-08-21 recon demonstrates why this qualification is mandatory: the gitignored generated
directory contained 31 READMEs, while its own current audit evaluated 30, reported 27 clean and three
current Mermaid hard-gate failures, and left Cells/TypeScript without the same verification/code-
disposition receipts. Those observations describe that snapshot only; future executions must perform
the stable synchronization and re-audit rather than preserve the counts as assumptions.

## Candidate-First Sequence

The near-term graph executes in this order:

1. reconcile this contract, the current graph, catalogs, hashes, evidence, and durable state;
2. refresh and independently qualify the evolving Aspose.org development oracle, freeze its
   visitor-quality profile, then close candidate identity, rubric, blocking-check, and receipt-
   compatibility gaps;
3. wire one complete candidate through the existing section-authoring and evidence path;
4. prove one sealed weak-input candidate at 30/30 plus immediate complete-transaction no-op;
5. encode that proven transaction behind typed allow-listed graph actions and predicates;
6. prove one complete candidate per supported ecosystem;
7. run the dynamic processable portfolio with per-repository isolation and failed-only repair;
8. reconstruct without new provider work, reproduce on a clean bounded runner, and perform an
   independent adversarial audit.

The general mission runner is deliberately after the first sealed candidate. It automates a
proven transaction rather than becoming a prerequisite for discovering what that transaction
must do. Later canary, fleet, hosted, and audit tasks enter the active horizon just in time.

## Safety And Closure

- `supervise` remains the only acceptance runtime.
- The graph and durable state remain the only task authority and cursor.
- Graph actions may invoke only typed allow-listed Python handlers; arbitrary shell is forbidden.
- A repairable failure creates a durable causal obligation and reopens only dependent stages.
- Two equivalent ineffective attempts require a first-principles replan before another attempt.
- No initial drift baseline may bless unknown state; it must derive from a verified plan freeze.
- Product repositories, product branches, draft PRs, and default branches are untouched during this
  campaign.
- Control-repository code repair remains coordinator-governed until automated mutation is separately
  proven safe; the initial mission runner does not author, commit, or push code.
- Focused checks follow each repair; complete official checks run at shared contract, graph-flip,
  fleet-freeze, and final campaign boundaries.
