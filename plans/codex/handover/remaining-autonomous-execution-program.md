# Remaining autonomous execution program

This is the continuation after the active README task. It preserves the user's required
local-first order and the Level-8 Waves 0-8 destination.

## Dependency flow

```text
active README proposal proof
  -> complete local central-agent resilience
  -> complete canonical workflow under act
  -> disposable GitHub staging proposal lifecycle
  -> repair mechanical dependency and reconcile pre-production gate
  -> production GitHub App/access handoff
  -> complete production runtime/product truth/presentation/proposal gates
  -> controlled Java Level-5 pilot
  -> heterogeneous Levels 6-7
  -> 90-day Level-8 proof
```

No later layer may compensate for a failed earlier layer.

## Phase A: complete local central-agent resilience

Taskcard:

```text
L8-LOCAL-CENTRAL-AGENT-RESILIENCE
```

Goal: prove the complete locally testable central agent from one command, not only README
contracts.

### Surfaces

- README proposal;
- repository description;
- homepage;
- topics;
- community-file audit and bounded file proposals;
- repository-owned visual preparation;
- truthful social-preview manual-UI handoff;
- package and release audit-only findings;
- GitHub-generated signal observations; and
- cross-surface consistency.

### Required scenarios

- first proposal;
- unchanged no-op;
- targeted upstream content change;
- simulated maintainer overwrite;
- malformed README;
- prompt injection;
- missing fact;
- conflicting fact;
- duplicate trigger;
- state read outage;
- state write outage;
- cancellation/resume at every lifecycle checkpoint;
- one controlled specialist failure; and
- evidence corruption.

### Required outcomes

- every surface has an honest terminal result;
- manual-only and audit-only surfaces never report applied;
- all three pilot bundles are independently accepted;
- manifests are complete, redacted, and checksum-valid;
- one failing lane does not stop unrelated eligible work;
- no product remote is touched; and
- the complete local run is reproducible from one command.

At closure the system may be described as a “locally proven pre-production
repository-presentation system.” It may not be called production-ready or Level 7/8.

## Phase B: complete workflow parity under `act`

Taskcard:

```text
L8-ACT-CANONICAL-WORKFLOW-PARITY
```

Goal: run the actual reusable workflow through every applicable job under Docker/`act`.

### Build/repair

- explicit local/staging authentication provider;
- isolated local bare Git remote for durable state;
- isolated disposable target fixture remotes;
- authoritative repository matrix from the planning job;
- recovery matrix;
- analysis/supervisor execution;
- evidence upload/artifact stage;
- health aggregation;
- workflow-level terminal propagation; and
- matrix failure isolation.

### Trigger proof

- `workflow_dispatch`;
- `repository_dispatch` with delivery identity;
- duplicate delivery;
- simulated scheduled recovery;
- checkpoint resume; and
- one matrix repository failure while others complete.

### Rejection criteria

The gate fails if:

- only the planning job runs;
- `supervise` is skipped;
- a fixture-only controller replaces the runtime;
- evidence or health jobs do not run;
- production profile accepts PAT/`GH_TOKEN`;
- a product remote is contacted for write; or
- workflow success masks a failed repository job without an honest aggregate result.

Capture Docker and `act` versions, workflow commit, full job logs, exit codes, isolated remote
state, and checksums.

## Phase C: disposable GitHub staging

Taskcard:

```text
L8-STAGING-VERIFIED-PROPOSAL-PROOF
```

Goal: prove exactly-once draft proposal effects against disposable GitHub repositories while
keeping target default branches byte-identical.

### Codex/agent-owned work

- specify deterministic disposable repository names;
- seed all three pilot archetypes;
- configure policies and authorization records;
- implement/complete `VerifiedPresentationCandidateV1`, `VerifiedProposalV1`, and
  `OpenProposalV2`;
- run the same workflow/runtime used under `act`;
- reconcile durable state with actual GitHub branch/PR state;
- execute and verify every lifecycle scenario;
- retain checksum-complete evidence; and
- archive/delete staging only with explicit authorization after evidence retention.

### Human-only input at this phase

The human supplies or approves:

- exact disposable staging repositories if the agent lacks repository-creation authority;
- a staging-scoped credential with minimum draft-PR permissions; and
- acceptance/reviewer authority.

The human does not run the workflow or create evidence.

### Required scenario matrix

- initial draft PR creation;
- unchanged retry/no-op;
- changed-candidate update;
- target-head drift and full rebuild/reverification;
- duplicate delivery;
- lost GitHub response;
- expired authorization;
- crash after branch creation;
- crash after commit push;
- crash after PR creation; and
- reconciliation from durable state plus GitHub observation.

### Hard assertions

- exactly one correct open proposal state;
- no force push;
- no default-branch mutation;
- no write token before the effect job;
- no effect with missing/expired/out-of-scope authorization;
- PR body contains facts, validators, verifier, rollback, and evidence;
- draft stays draft; and
- settings remain a separate authorization/effect.

## Phase D: pre-production reconciliation and production access request

Before production:

1. repair the graph dependency described in
   `current-state-and-worktree-boundaries.md`;
2. reconcile `L8-014`, the task graph, durable state, and the master plan;
3. obtain fresh approval for any exact `plans/master.md` sections to update;
4. independently reproduce local, `act`, and staging evidence; and
5. issue the human an exact, minimal access request.

The access request must state:

- GitHub App name;
- repository/organization installation scope;
- contents, metadata, pull-request, issue/check, and settings permissions actually needed;
- which permissions are read versus write;
- secret names and where workflows reference them;
- private-key/client/installation identifiers;
- webhook/callback needs, if any;
- production authorization record format;
- dead-man endpoint credential;
- analytics credential; and
- exact validation command and resume condition.

Do not ask for production access before this phase.

## Continuous behavior across all phases

After every bounded task:

1. inspect raw results;
2. run focused and regression verification;
3. run an independent evidence lane;
4. repair findings;
5. update requirements, evidence, logs, and durable task state;
6. commit coherent work on `main`;
7. claim the next eligible task; and
8. continue without waiting for a routine “go ahead.”

A failing lane does not stop unrelated eligible work. Only a proven external authority/access
boundary or mission completion is a valid autonomous stop.
