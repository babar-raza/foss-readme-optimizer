/loop

1. Refresh Git branch/HEAD/status, repository-owned processes, registry and graph hashes, durable
   mission status, active claim, and claim expiry. Narrative files never override state.
2. Run mission `evaluate` after restart, expired claim, graph/registry change, or invalidation.
   Claim only the printed task as `claude-coordinator`; never steal a live claim.
3. Load only the claimed taskcard, direct dependencies, current repository scope, last valid stage,
   and acceptance evidence. Preserve unrelated work, especially `plans/backlog-post-poc.md`.
4. For the existing Python parent, reconcile completed strict/exception evidence and graph-required
   transport/admission without re-auditing or redesigning Python READMEs.
5. For non-Python work, prove one representative pilot for the current platform before batching.
   Derive all facts, packages, APIs, examples, links, formats, requirements, and limitations from
   the current target repository and authoritative registry; never translate Python assumptions.
6. Repair the smallest causal owner, then run focused static/tests and the impacted integration,
   safety, recovery, rendering, evidence, and idempotency checks. Do not weaken a validator.
7. Inspect source reconciliation, candidate, patch, claims, official Mermaid SVG, rendered
   presentation, example proof, links, deterministic result, and independent review.
8. Run a later complete fresh process. Require byte-identical output, no patch, no duplicate
   lifecycle/effect, zero unnecessary provider calls, and justified cache reuse.
9. Obtain a non-authoring independent PASS. Write redacted checksum evidence, promote only when
   strict state permits, transition with evidence, evaluate, and continue.
10. After two equivalent failures or 15 minutes without narrowing, stop that tactic, identify the
    false assumption, persist a first-principles replan, and change owner/mechanism/sequence.
11. Use only disjoint repository workers after one pilot proves isolation; the coordinator owns all
    shared files, state, integration, commits, and closure.
12. Perform no product push, PR, merge, package/release publication, or default-branch write without
    the existing fresh exact what/why/where approval gate.

Continue through `.NET`, Java, C++, TypeScript, Rust, and Go in configured order. Do not stop at a
pilot, platform, commit, test failure, report, session boundary, checkpoint, or agent-fixable block.
Stop only for a genuine unavailable external authority/infrastructure/manual action that prevents
all remaining eligible work, or when the handoff definition of done is independently proven.
